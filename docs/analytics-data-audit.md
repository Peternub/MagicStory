# Аудит данных SkazKIDS Analytics MVP

Дата аудита: 20 августа 2026 года.

## Область аудита

Проверены миграции PostgreSQL, функции генерации, Better Auth, AI Gateway и deployment-конфигурация текущего репозитория. Подключение к production PostgreSQL в локальном окружении отсутствует, поэтому аудит подтверждает назначение и доступность полей, но не полноту фактических production-данных. Перед деплоем аналитики нужен read-only smoke test запросов на VPS.

## Метрики, доступные достоверно

| Метрика | Источник | Правило расчёта | Ограничение |
|---|---|---|---|
| Новые пользователи | `public.user.createdAt` | Количество регистраций в интервале | Основной источник регистрации — Better Auth, а не `profiles` |
| Созданные профили детей | `public.children.created_at` | Количество созданных строк в интервале | Удалённые профили исторически не видны из-за физического удаления |
| Созданные сериалы | `public.story_series.created_at` | Количество созданных строк в интервале | Включает неуспешно запущенные сериалы; успешность показывается отдельно |
| Созданные эпизоды | `public.stories.created_at` | Количество зарезервированных эпизодов в интервале | Не равно числу успешных генераций |
| Успешные генерации | `public.usage_events` | `event_type = 'series_episode_created'`, время — `created_at` | Событие записывается только после успешного завершения и защищено от дублей |
| Неуспешные генерации | `public.stories` | `status = 'failed'`; для периода временно используется `updated_at` | Повторный успех перезаписывает статус, поэтому история попыток теряется |
| Пользователи, впервые создавшие сериал | `public.story_series` | Пользователь, у которого первый `created_at` попал в интервал | Факт создания не подтверждает успешную генерацию первой серии |
| Пользователи, продолжившие сериал | `public.stories` | Уникальные `user_id` с `episode_number >= 2` и `created_at` в интервале | Считает создание эпизода, успешность нужно фильтровать через `usage_events` |
| Эпизоды на активного пользователя | `public.usage_events` | Успешные эпизоды / уникальные создавшие их пользователи | Активность ограничена генерацией контента |
| Episode continuation rate | `public.stories` | Доля пользователей с успешным эпизодом 2 среди пользователей с успешным эпизодом 1 | Нужен минимальный размер когорты; иначе `insufficient_data` |
| Next-day return proxy | `public.usage_events` | Пересечение пользователей с успешной генерацией в соседние календарные дни | Это proxy возврата к генерации, а не полный возврат в продукт |
| Провайдер/модель успешной генерации | `public.stories.provider_llm`, `public.story_series.model_code` | Группировка успешных эпизодов | `provider_llm` фактически содержит модель из ответа gateway; отдельного поля provider нет |
| Оплаты | `public.payments` | Статусы, суммы и `paid_at` | Раздел нужно скрывать, пока billing не активирован конфигурацией |
| Starter offer | `public.starter_offer_orders` | Статусы, суммы, `paid_at` | Не смешивать с обычными платежами без явной нормализации |

## Определение DAU для MVP

До появления продуктовых событий активным считается пользователь, который успешно создал хотя бы один эпизод за период. Источник — `usage_events` с `event_type = 'series_episode_created'`. Сессии Better Auth не используются: обновление сессии не доказывает значимое действие.

Это определение намеренно узкое. Открытие или продолжение чтения сериала пока не записывается и не должно выдумываться по `updated_at`.

## Метрики, которые сейчас нельзя посчитать достоверно

| Метрика | Причина |
|---|---|
| Открытие/чтение/продолжение существующего сериала | Нет продуктового события просмотра |
| Полный DAU | Нет единого журнала значимых действий |
| Количество AI-запросов и повторных попыток | В БД хранится итоговый статус эпизода, а не каждая попытка |
| Исторический AI error rate | Ошибка может быть перезаписана последующим успешным retry |
| Средняя и p95 AI latency | `generation_started_at` очищается после завершения; duration остаётся только в journald gateway |
| Input/output tokens и стоимость | Gateway получает usage, но не сохраняет его в PostgreSQL |
| Надёжная категория AI-ошибки | В `stories.error_message` сохраняется пользовательский текст, а не стабильный код |
| Backend errors и HTTP 5xx | Нет структурированного журнала или агрегата приложения |
| Retry rate | Нет номера/идентификатора попытки в постоянном хранилище |
| Уникально затронутые пользователи инцидента | Ошибки не хранятся как отдельные события |

## События и таблицы, необходимые для MVP

### `analytics_generation_events`

Одна строка на каждую попытку AI, без текста сказки и персональных данных:

- `request_id` — технический хеш, не production ID;
- `occurred_at`;
- `status`: `started`, `succeeded`, `failed`;
- `provider` и `model`;
- `latency_ms`;
- `input_tokens`, `output_tokens`;
- `error_category` из закрытого списка;
- `attempt`;
- `story_id` допустим только внутри production БД и никогда не отправляется AI.

### `analytics_product_events`

Минимальные обезличенные события:

- `series_opened`;
- `episode_opened`;
- `series_creation_started`;
- `series_creation_completed`;
- `episode_creation_completed`.

В MVP достаточно добавить `series_opened` и `episode_opened`, если нужен DAU шире генерации. Payload должен иметь закрытую схему и не содержать имён, текста сказки, email или session ID.

### `analytics_daily_snapshots`

Ежедневный агрегированный JSON, health state, AI cost и метаданные доставки отчёта. Персональные данные и сырые логи запрещены.

### `analytics_alert_state`

Состояние cooldown и восстановления для каждого стабильного кода alert. Это предотвращает повторную отправку одного инцидента.

## Технические источники вне PostgreSQL

- Backend: `GET http://127.0.0.1:3000/api/health`.
- AI Gateway: локальный `/health`, если сервис настроен.
- PostgreSQL: короткий `select 1`.
- Сервисы: `systemctl is-active`, без полного вывода `systemctl status`.
- Backup: возраст последнего валидного файла `/var/backups/skazkids/postgresql/skazkids-*.dump` и состояние `skazkids-postgres-backup.service`.
- Disk/RAM/load: локальные системные показатели VPS.
- Nginx: `systemctl is-active nginx`.

## Индексы, необходимые аналитическим запросам

Текущих индексов по `user_id` недостаточно для периодических выборок. В миграции MVP нужны индексы:

- `user(createdAt)`;
- `children(created_at)`;
- `story_series(created_at)` и `(user_id, created_at)`;
- `stories(created_at)`, `(status, updated_at)` и `(series_id, episode_number, status)`;
- `usage_events(event_type, created_at)` и `(user_id, event_type, created_at)`.

## Итог аудита

Текущая схема достаточна для первого отчёта по регистрациям, созданию контента, узкому DAU и retention proxy. Для технической AI-аналитики нельзя использовать итоговые строки `stories`: требуется отдельный неизменяемый журнал попыток. Для полного DAU нужно начать записывать значимые продуктовые события. Все неизвестные значения должны возвращаться как `insufficient_data`, а не как ноль.
